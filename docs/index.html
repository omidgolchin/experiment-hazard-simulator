How big is the eval?

Distinct problems in your eval set. This is usually what limits precision, more than attempts.
Runs of each task per version. Agents are random, so repeats average out luck on each task.

Why this matters: tasks are the evidence — each one is an independent problem. Attempts only average out an agent's luck on a task it has already seen.

Why this matters: the verdict is judged against the smallest improvement you would act on. Aiming at a gain half as big needs roughly four times the tasks.

How are the tasks set up?

From a pilot: if most tasks pass about as often as the overall rate, pick Similar; if many are always solved or never solved, Very mixed. Not sure? Mixed is the middle; try Very mixed to see the cost.
Running both versions on the same tasks cancels out task difficulty and needs far fewer tasks.

Why this matters: if tasks vary wildly in difficulty, that variation floods the comparison — unless both versions run the same tasks, so the difficulty cancels out.

How the verdict is computed model, simulation, sources

Model. Each task has a difficulty (normal on the log-odds scale; "similar", "mixed" and "very mixed" are standard deviations of 0.5, 1 and 2), and each attempt adds noise (0.5). Version B's improvement is set so that the average success rate rises by the points you entered. Your current success rate sets the baseline.

Analysis. With the same tasks for both versions: a paired t-test on per-task differences in success rate, because the task, not the attempt, is the unit that varies. With separate task sets: a Welch t-test on per-task success rates.

Chance to detect is the share of 1,500 simulated evals of the clean design (no risky answers) that find B significantly better at the 5% level. Fake wins is the share of simulated evals with no real difference that find a significant one, with your checklist answers applied; a sound design sits near 5%. Tasks for 80% comes from the standard formula n = ((z0.975 + z0.8) · sd / gain)², with sd the simulated spread of per-task differences, and the chart confirms it by simulation.

The checklist is the hazard list of the agent-experiment-methodology skill (agent-hazards.md), each with the check that catches it. Background: Hurlbert (1984) on pseudo-replication; Simmons, Nelson & Simonsohn (2011) on selective reporting; Panickssery, Bowman & Feng (2024) on LLM judges favoring their own outputs.

The simulation studies behind this tool (how each hazard's false-alarm rate grows with its strength) are summarised under Where this tool comes from, with the full study in its own repository. All data on this page are simulated.

How the results are analyzed paired by task, bootstrap

Each task's success rate is computed for each version, and the analysis runs on the per-task differences: a paired t-interval and, as a check that does not assume normality, a percentile bootstrap that resamples tasks (2,000 resamples). Tasks that ran on only one version are left out and listed.

The "attempts as independent" interval is what you get by pooling all attempts into two success rates. Attempts on the same task are correlated, so that interval is usually too narrow when the versions ran on different tasks; with shared tasks it can also be too wide, because it ignores the pairing. Either way it answers the wrong question.

When to use it, and when not assumptions, limits, alternatives

Use it before running an eval that compares two versions of an agent, prompt or model on a fixed set of tasks scored pass or fail, to size it and fix the design; and after it, to read the result per task rather than per attempt.

It assumes the following. Each line says what happens to the answer when your case breaks the assumption.

AssumptionIf yours differs
Each attempt is scored pass or fail.Graded scores (a 1-to-10 judge rating, partial credit) need a different model. As a first cut, set a pass threshold and use pass rates.
Tasks differ in difficulty, and attempts on the same task succeed or fail together.This is what makes the task the unit of analysis. If your tasks are near-identical, pooling attempts matters less.
The improvement is the same size on every task.Real improvements are larger on some tasks and zero on others. The chance to detect is then lower than shown; ask for a larger task count.
Each hazard's strength is a setting you choose (the default is a realistic middle value).The tool shows the mechanism and its scale, not how strong a hazard is in your eval. Move the slider to the strength you suspect.
The comparison is between two versions.For several versions, compare each with the baseline and correct for the number of comparisons, or plan a larger eval.
Success rates are not near 0% or 100%.Near the extremes, few tasks carry information. Make the task set harder or easier first.

Do not use it for open-ended human preference studies (use a paired-preference design with its own power analysis), for tracking a single model's score over time, or as proof that an eval is sound: a clean verdict means the hazards it checks are handled, not that the tasks measure what you care about.

Where this tool comes from the problem and data it was built on, and how it was generalised

The tool comes out of a study, "How design hazards fake wins in LLM-agent experiments". It simulated two conditions with no real difference, added one design hazard at a time, and counted how often the study would still report a significant improvement. With no hazard the rate is 5%, as it should be. With one:

  • Best-of-3 for the new version alone gave fake wins in 91% of evals.
  • Picking the best of five metrics gave 22%, and an unblinded judge that flips 20% of the new version's failures gave 20%.
  • Pooling attempts as if independent gave 13% when each condition had its own tasks, and was harmless when tasks were all alike.
  • Dropping crashed hard tasks barely moved the fake-win rate: it costs power, not validity.
  • Small studies also miss real effects: at 20 tasks a clean design detected a modest effect only 10% of the time.

How it was generalised. The study fixed 20 tasks, 5 attempts and a 50% success rate, with separate task sets per condition. The tool runs the same simulation on your design: your task count, attempts, success rate, hoped-for improvement and pairing (both versions on the same tasks is the default, which the study did not cover), with each "no" in the checklist simulated on its own so the verdict can rank what to fix. It adds a results checker and an AI reader for methods sections; the reader only answers the checklist from the text, and the statistics stay in code.
